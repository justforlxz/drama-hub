# ADR-0004：缓存淘汰交给 rclone，本服务不实现第二套 LRU

状态：**部分被取代**（2026-10-30，ADR-0007）。被取代的部分：本 ADR 的 2 条「本服务只做两件事」中，第 1 条（只生成 rclone 配置建议）与「不做自研 LRU」不再成立——`.strm` 改为指向本服务自己的 `/video/{id}.m3u8` 后，rclone 退出播放链路，缓存与淘汰必须由本服务承担（`docs/CACHE-MODEL.md`）。仍然成立的部分：`artifact` 只管封面 / 关键帧索引 / 分片索引，不承载视频淘汰策略之外的业务语义。

## 决策

- 分片缓存由缓存代理（rclone `serve http`，`--vfs-cache-mode full`）负责淘汰；
  本服务**不实现**自研 LRU、不设 `cache_max_mb` / `cache_lru_days` 运行参数。
- 本服务只做两件事：
  1. 在 WebUI/文档里**生成 rclone 配置建议值**（`--vfs-cache-max-size`、`--vfs-cache-max-age`），
     作为一次性输出，不参与运行逻辑；
  2. `pin_days` 驱动「最近 N 天播过的合并集整集预取」，预取本身也只把分片喂给缓存层，
     不自己记账淘汰。
- 本服务的 artifact 缓存只管**封面图与关键帧索引**（量小、结构不同），与视频分片缓存互不干扰。

## 为什么

- 视频分片是缓存代理在传输层做的，它拥有每个分片的访问历史与本地占用，**天然适合做 LRU**。
- 本服务再写一套 LRU 是在传输层之上复读同样的信息，两套淘汰策略会对同一批分片互相干扰
  （本服务按"最近播放"淘汰，rclone 按"最近访问"淘汰，策略不同会打架）。
- 两套 LRU 还会互相掩盖故障，排障时不知道该信谁。

## 代价与边界

- 淘汰的精确控制（如"只保留正在追的剧"）依赖 rclone 的缓存参数，无法在本服务内细粒度控制。
- `cache_max_mb` / `cache_lru_days` 不作为运行配置：它们只在"建议的 rclone 配置"里体现。
