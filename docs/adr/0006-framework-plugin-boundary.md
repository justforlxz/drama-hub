# ADR-0006：框架与播放源插件的边界

状态：提议，待 PL 确认后改为「已接受」（2026-10-30，MKACG-604 / stage 1 设计）
上游依据：MKACG-603 总控「插件实现具体功能，框架负责调度与执行」

## 背景

1.0 只有一个数据源，`internal/provider` 里是一个具体 `Source`：它同时做三件事——
请求上游、解析页面、**用 `*store.Store` 直接写库**（`SyncSeries(ctx, st, sid)`）。
`providerName = "web"` 是包级常量，全仓没有 plugin / registry / register 符号。

2.0 要让「红果」变成第一个插件。在没有先定边界的情况下改造，最常见的两种退化是：
插件变成一层的假抽象（接口里带着 `sid` / `vid`），或者框架退化成插件的私有调用方
（插件自己开事务、自己调度）。

## 决定

边界按「谁拥有真值」划：

- **插件 = 上游的翻译器。** 只做「把上游字节翻译成框架的领域值」，不做 I/O 之外的事：
  - 不 import `internal/store`、`internal/vfs`、`internal/web`、`internal/schedule`；
  - 不写库、不开事务、不决定幂等身份；
  - 不持有调度器、不认识时间轮；
  - 只通过返回值与哨兵错误表达结果。
- **框架 = 唯一写库者、唯一调度者、唯一派生者。** 事务边界、`(provider, provider_id)`
  幂等身份、`emby_item` 重建、WebDAV 树、直链请求时解析，全部在框架侧。
- **插件没有 `Refresh` 方法。** 刷新 = 框架按调度重新调用 `Work` / `Resolve`。
- **插件名即写库标识。** `Plugin.Name()` 的返回值直接进 `drama.provider` /
  `episode.source`，必须稳定。

具体接口、错误语义、注册与配置见 `docs/PLUGIN-CONTRACT.md`。

## 被否决的划法

1. **插件持有 `*store.Store` 自行落库**（1.0 的现状，`SyncSeries(ctx, st, sid)`）。
   否决理由：谁能写库谁就决定了事务边界、幂等身份与失败隔离，框架无法再保证
   「上游失败 → 库不变」；插件单测要真数据库；第二个插件会把同一套事务逻辑
   抄第二遍。现有 `SyncSeries` 的签名因此必须改掉，这不是重命名而是语义收敛。
2. **插件是独立进程 / 独立 HTTP 服务（真·plugin）**。
   否决理由：与硬约束 4（单二进制 + PostgreSQL、无第二个应用运行时）直接冲突；引入进程边界
   还要额外定义序列化、生命周期、崩溃重启，换来的只是插件开发者不必 import 本仓。
3. **接口按上游字段建模**（`SyncSeries(sid)` / `FetchDirectURL(sid, vid)`）。
   否决理由：第一个插件会被固化成框架的字面量，第二个源要么被迫伪造 `sid`，
   要么改接口。`sid` / `vid` / `spade_a` 这类名字只允许出现在插件实现内部。
4. **插件自带调度**（`Plugin.Refresh(ctx, interval)` 或插件自己起 ticker）。
   否决理由：调度需要全局视野——同源单飞、与手动触发互斥、失败隔离、状态页，
   这些做不到「每个插件自己来一遍」而不重复实现。而且插件一旦起 goroutine，
   测试就没有可停的边界。
5. **`init()` 自注册**。否决理由：依赖方向反转（实现包被框架隐式 import），
   测试无法决定注册哪些假插件，注册顺序不可控。改为装配根显式注册。

## 后果

- 新增一个源 = 实现 4 个方法 + 在 `cmd` 装配根注册两行，不改框架。
- 框架侧的通用能力（如「批量拉取」）如果要进步，就得动接口；这是有意接受的代价：
  接口改动集中在一个包，比让每个插件各自实现一遍便宜。
- 红果插件 `Name()` 返回 `"web"` 而非 `"hongguo"`：库中已有 `provider = 'web'` 的数据，
  改名要写数据迁移，而 2.0 没有「同一剧目出现在两个源」的需求。理由与备选见
  `docs/DATA-MODEL.md`「provider 标识」。
- `internal/store` 不认识插件：它只知道 `provider` 是字符串。
- 依赖层次：`internal/plugin`（rank 20，只依赖标准库）、`internal/plugin/<源>`（rank 30，
  可依赖 20/10）、装配根 60。`internal/` 其余包不得 import 任何 `internal/plugin/<源>`。

## 2.0 的边界外（不在本 ADR 的"框架"里，也不在插件里）

这三件事有明确的旧决策或明确的不做理由，写在这里是为了让实现期不用反复讨论：

| 项 | 归属 | 依据 |
|---|---|---|
| **缓存层实现** | rclone `serve http`（不是本服务的框架，也不是插件） | ADR-0004：本服务只驱动与刷新，不实现任何缓存淘汰；`artifact` 只管封面与关键帧索引 |
| **App 接口回退 + `spade_a` 解密** | 不做 | `AGENTS.md`「做什么/不做什么」已列；本次实测确认官网 SSR 自足（枚举、详情、集列表全都有），回退路径不是 2.0 的必需件 |
| **多用户 / 多租户 / 权限** | 不做 | `AGENTS.md` 同上；WebDAV 只有一层 Basic 认证（`webdav_user` / `webdav_pass`），没有「谁看过什么」的状态 |

框架与插件都不为上面三项预留接口：没有 `Cache` 方法、没有 `Fallback` 方法、
没有 `User` 参数。需要时再写新的 ADR，不在 2.0 的接口里留钩子。
