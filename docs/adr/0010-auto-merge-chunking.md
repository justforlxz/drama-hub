# ADR-0010：合并集由 settings 的 N 自动分块，删掉手工编排

状态：**已接受**（2026-11-02，MKACG-649）。口径来源：lxz 2026-11-02 的需求重述与
Planner 的契约评论（`merge_chunk_size` 默认 10、范围 1–500、纯派生、手工编排整体移除）。

> **部分被 ADR-0014 取代（2026-11-03，MKACG-666）**：本 ADR 的第 1/2/3/7 条与它依赖的
> `emby_item` 派生表一起废弃 —— 分块结果不再落库，也不再有「下一次重建」。分块规则
> （列表连续切片、uid 形态、块内 single/merged 判定、被否决方案）保持不变，仍然有效。

## 背景

1.0/2.0 初版的合并集是**人工编排**：`/merges` 页面选剧、按想要的顺序点集、建组，
组落在 `merge_group` / `merge_item` 两张表里，`RebuildEmbyItems` 读这两张表再算派生表。

实测红果一集只有 53–67 秒，Emby 里一集几十秒没法连续看。需求是「**几集并成一集**」，
而且合并应当是**自动的**：

- 默认 10 集并 1 集；
- 合并数量在后台可配置、改完下一次重建即生效（不重启）；
- 不需要人去挑集、建组。

人工编排满足不了「每部剧都自动合并」：它要求人对每部剧做一次编排，而库里有几万部剧。

## 决定

1. **N 是 settings 键 `merge_chunk_size`**（默认 10，范围 1–500），每次重建现读、不进程内
   缓存（`AGENTS.md` 硬约束 5）。不做按剧覆盖。
2. **分块是纯派生**：取该剧 `episode`（`ORDER BY ep_no`）按 N 切**连续列表切片**
   （不是 `ep_no` 数值区间——缺号不产生空位），第 i 块 → `emby_item.ep_no = i`；
   对外集数 = `ceil(集数 / N)`；0 集 → 0 行，不留空组。
3. **块内 1 集 → `kind=single`、uid `e<episode.id>`；≥2 集 → `kind=merged`、
   uid `m<dramaID>_<epFrom>_<epTo>`**、`runtime_sec = Σ成员时长`、标签「第 A-B 集」
   （A==B 退化「第 A 集」）。`emby_item` 仍是唯一派生表（硬约束 6）。
4. **uid 只由 `(dramaID, 成员集号区间)` 派生**，不含自增主键：`emby_item` 整体重建、
   `merge_group` 表消失之后，「集集合与 N 不变 → 重建后 uid 逐字符不变」仍然成立。
   分隔符用 `_` 不用 `-`：播放 id 是 `<uid>-<签名>`，`stream.ParseID` 按首个 `-` 切，
   uid 里带 `-` 会把「uid 不存在」的 404 顶成「签名不对」的 401。
5. **`merge_group` / `merge_item` 删除**（migration `0005`），`/merges` 页面、三个
   merge API、`merge_groups` 计数一起去掉。自动分组是唯一来源，不保留「两者冲突谁优先」的
   兼容层。需要「某部剧临时特殊合并」时再加回来（本次不做）。
6. **播放面不变**：仍是虚拟 HLS 分片聚合、集边界 `#EXT-X-DISCONTINUITY`、不物化；
   `/video/{id}.m3u8` 与 `{id}/{seq}.ts` 形态、目录形状、`.nfo` 结构都不动。
   合并块展开成员用 `emby_item` 的 uid 反解出 `(dramaID, ep_from, ep_to)`，再按
   `ep_no ∈ [a,b]` 取集（列表连续切片保证区间内没有别的块）。
7. **旧 id 失效沿用既有 404 分支**：改 N 后旧 uid 不在 `emby_item` → `/video/{oldid}` 404
   （签名仍合法，不得变 401、不得返回别人的内容）。分片/索引缓存不做主动回收，
   靠 `cache_lru_days` / `cache_max_mb` 过期（`docs/CACHE-MODEL.md`）。
8. **不新增全库重建入口**：N 的生效点沿用既有重建调用点（同步完成、首播回填）。
   全库重建 ≈ 2847 万集，请求内做不完，做了就是给自己造一条会超时的死接口。

## 被否决的方案

1. **保留 `/merges` 手工编排，自动分组作为默认值。**
   否决理由：两套真相必然要回答「人改过的组还自不自动重算」，而任何答案都要一份
   覆盖标记 + 一套冲突规则 + 对应的界面状态。需求是「不做人工编排」，先删干净。
2. **把分块结果落库成新表 `merge_block`（像 merge_group 那样）。**
   否决理由：多一张派生表和一次「什么时候重建它」的同步问题；分块是纯函数，
   直接算进 `emby_item` 就够，硬约束 6 也要求对外集号只由派生表决定。
3. **按 `ep_no` 数值区间分块**（第 1–10、11–20…）。
   否决理由：库里集号可能有缺号（源侧下架/删除不删行），数值区间会切出空块、
   或让某块只剩 1 集却按 merged 规则标注。列表连续切片没有这个问题。
4. **uid 用 `emby_item.id` 或 UUID。**
   否决理由：`emby_item` 整体重建会换自增 id → URL 飘、缓存全废（ADR-0007 已驳回一次）。
5. **改 N 后主动清空分片缓存。**
   否决理由：旧 uid 不再出现在派生表里，旧分片永远不会被新 URL 命中，留着由 LRU 处理即可；
   主动清空要遍历缓存目录、还要设计「清哪些」，净增复杂度没有收益。
6. **按剧覆盖 N。**
   否决理由：需求只到「全局可配」；按剧覆盖要新表/新列 + 界面 + 优先级规则，等 lxz 提出再加。

## 后果

- 改 N 会重排全库对外集号、让所有合并 uid 失效：Emby 侧按集号的观看进度会对不上。
  这是需求本身（lxz 已接受「旧 id 失效」），不做补偿。
- 某区间内集数新增/变化会让覆盖该区间的块成员变化 → 该块 uid 变，Emby 视作新集。
- `merge_group` / `merge_item` 的数据随迁移 `0005` 丢失，不可逆。
- **派生表不做数据迁移**：旧合并行的 uid 是 `m<merge_group.id>`，新代码的形态真值
  （`store.ParseMergedUID`）解不了它，留着会让该剧季目录的列举直接报错。迁移顺手
  清掉这些行；受影响的剧在下一次重建（同步完成 / 首播回填）之前只显示单集，之后按
  当前 N 补回正确的块。
- 净删代码：3 个 handler、1 个页面、约 180 行手工编排 store 代码与 2 张表，
  换 1 个 settings 键、1 个纯函数、1 个区间查询。
