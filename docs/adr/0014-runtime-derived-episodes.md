# ADR-0014：对外剧集只在运行时现算，`emby_item` 表删除

状态：**已接受**（2026-11-03，MKACG-666）。需求来源：lxz「数据库只存原始集，合并只在
运行时访问时动态合成」。取代 ADR-0010 的第 1、2、3、7 条与 `emby_item` 派生表本身；
ADR-0010 的分块算法（列表连续切片、uid 形态、块内 single/merged 规则）不变。

## 背景

ADR-0010 把「几集并成一条对外剧集」做成纯派生，但**派生结果仍落在 `emby_item` 表里**，
生效点是「下一次重建」：同步完成（`internal/sync`）与首播回填时长
（`store.BackfillEpisodeDuration`）。lxz 在真机上看到的现象是：

> 生成的数据仍然是独立的一集，后续访问以后才变成十合一。

成因就是这张表：库里存的是**上次重建那一刻**的分块。改 `merge_chunk_size` 之后，
目录与 `.m3u8` 要等下一次同步（可能几十分钟、也可能永远不触发）才变；先灌库后改 N 时，
用户看到的是「一集一个」，过一阵才「十合一」。这不是缓存问题，是**同一件事的第二份
真值**：原始集在 `episode`，合并结果在 `emby_item`，两者何时对齐没有任何机制保证。

## 决定

1. **`emby_item` 表删除**（migration `0008_drop_emby_item.sql`）。库里只存原始集
   （`episode`）与当前配置（`settings.merge_chunk_size`）。
2. **对外剧集是纯函数**：`store.embyItems(dramaID, eps, n)` 把按 `ep_no` 升序的集列表
   按 N 切连续块（复用既有 `chunkEpisodes`）。`store.EmbyItem` 不再是表行，因此没有
   自增主键；`uid` 仍是单集 `e<episode.id>`、合并集 `m<dramaID>_<epFrom>_<epTo>`，
   与 ADR-0010 逐字符相同 —— 已发出的播放 URL 在同一 N 下继续有效。
3. **读路径只有一个入口**：`store.ListEmbyItems(ctx, dramaID)` = 1 次现读 N + 1 次列
   `episode`。vfs 的目录列举、`.nfo`、`.strm` 全部走它；`store.EmbyItemByUID` 现算当前
   分块并**一并返回成员集**，播放面不再自己反解区间再查一次。
4. **改 N 立即生效**：不需要同步、不需要重建、不需要重启。同一 N 下重复读逐字符相同；
   改 N 后旧 uid 立刻不在当前分块里 → `/video/{oldid}` 404（签名仍合法，不得 401、
   不得返回别的形态的字节）。
5. **查询次数常数、与集数无关**：一集播放路径 2 次查询（合并集：现读 N + 列集；
   `drama_id` 从 uid 解出）、3 次（单集：多一次 `episode` 行取 `drama_id`）。原来
   「查派生表 + 查区间/单集」也是 2 次，所以最坏多 1 次点查，没有引入按集数增长的查询。
6. **计数口径跟着变**：管理面 `emby_items` 计数从「派生表行数」改成
   `ceil(集数 / N)`（`store.ListDramaStats` 里现算），字段名与语义保留，页面不用改。
7. **回填时长不再重建任何东西**：`episode.duration_sec` 写进去，下一次读就是新的
   `runtime`（`.nfo` 的 `<runtime>`、playlist 的 `EXTINF`）。锁序保持 `drama → episode`。

## 被否决的方案

1. **A 派生表按需重建（配置版本变了就先重建该剧）。**
   否决理由：要给 settings 加一个「版本号 / 脏标记」，每次读都多一次比较，还要写库；
   而重建的结果本来就能一次算完 —— 相当于为了保留一份可复制的缓存，新增一套失效协议。
   收益只有一个「读时不花算力」，而这里的算力是一次内存切片。
2. **把 `emby_item` 改成 SQL 视图。**
   否决理由：分块依赖 `settings.merge_chunk_size`（一行 JSON 配置）与「列表连续切片」，
   在 SQL 里要 `row_number() / n` 拼窗口函数 + 读配置，读起来比 30 行 Go 差，且
   `uid` 的拼装规则会分裂成 SQL 与 Go 两份。
3. **保留表但只在读取时校验并懒重建。**
   同上，且保留表就保留了「库里有一份可能过期的对外集号」这个缺陷本身。
4. **改 N 后全库重建一次。**
   否决理由：ADR-0010 已否决过一次 —— 2847 万集不可能在请求内做完；现在这个方案
   连「什么时候重建」都不需要回答了。

## 后果

- **收益**：改 N 是纯配置操作，`ls` 与 `.m3u8` 下一次请求就是新分块；少一张表和一套
  「什么时候重建」的调用点（同步、回填两处代码消失）；没有过期数据可言。
- **代价**：目录列举比原来多一次查询（现读 N），播放面单集路径多一次点查；`emby_item`
  里那份「预计算结果」不再存在，每次列举都要切一遍切片（单剧几十到几百条，测不出来）。
- **行为变化**：以前改 N 后要等一次同步才变，现在立刻变 —— 与本 issue 的需求一致；
  Emby 侧的集号在一次扫描内会整体重排（与 ADR-0010 相同的既有后果）。
- **`0008` 不可逆**：表直接删，不迁数据（每行都能现算，等价）。
- **`web/api` 的 `emby_items` 字段不变**：值改成现算的 `ceil(集数 / N)`。
