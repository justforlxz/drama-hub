# ADR-0015：目录结构与 PROPFIND 响应在进程内缓存，写入与配置变更整体失效

状态：**已接受**（2026-11-04，MKACG-669）

## 背景

`internal/vfs.Tree` 原本无状态：每次 `List`/`Render` 都从数据库现算整层结构，一次请求
算完即丢。MKACG-656 的实测（真实同步库，最大分类「剧情」8,329 子项）：

| 场景 | Depth:1 PROPFIND | 响应体 |
| --- | --- | --- |
| 8,329 子项分类目录 | 0.22–0.27s | ≈4.5MB |
| 造数 10 万子项 | 2.46–2.53s | 57.89MB |
| 造数 21.8 万子项 | 4.52–6.03s | 116.52MB |

21.8 万档已经超出 MKACG-651 契约线（≤5s / ≤200MB / ≤100MB 响应体）16%。
验收目标（lxz 2026-11-04 认可，硬门槛）：

> 8,329 子项分类目录 PROPFIND **命中缓存 ≤50ms**；未命中首次值与 P50/P99 一并记录。

## 测量：钱花在哪

先用同一份 8,329 子项数据对本机跑一次带 CPU profile 的 PROPFIND（Depth:1）：

- 墙钟 **254ms**，body 4.5MB，VmHWM 25→27MB；
- `vfs.(*Tree).List` 自身 **约 30ms**（DB 全列 29ms / 窄列 15ms，已由 651 收窄到窄列）；
- `x/net/webdav.handlePropfind` 0.25s，其中 `walkFn`（逐子项构建 propstat）0.22s、
  `encoding/xml` 的 `marshalValue`/`marshalStruct` 约 90ms、`multistatusWriter.write`
  0.09s。

**结论：只缓存 `[]vfs.Node` 最多把 254ms 降到约 224ms，离 50ms 差一个数量级。**
剩余成本几乎全在「把结构序列化成 207 响应体」。所以要达标，缓存必须落在**响应层**，
而不仅是结构层。

## 决策

两层缓存，都在进程内存，都不落盘：

### 1. 结构缓存（`internal/vfs`，按目录分片）

- 键 = 目录路径（根 `""` 与 `"短剧"` 归一为同一个键）；值 = `[]Node` + 生成时的版本号。
- 版本号 `store.TreeRevision()`：进程内单调计数器。**任何影响树结构/文件长度的写入
  成功后 +1**，且必须在事务提交之后（否则读者可能把旧数据存到新版本号下，永久读旧值）。
- 命中条件只有「版本号相等」；版本号一变，所有目录一次全失效。保守，但正确性优先：
  失效漏一条就是永久读旧数据，而全失效只是一次冷算。
- 触发版本的写入：`UpsertDrama`、`UpsertEpisode`、
  `BackfillEpisodeDuration`、封面类 artifact 的 `Put`/`Delete`/`Release`，
  以及 `Settings.Set`/`SetMany`/`SetIfAbsent`。播放路径的 `TouchArtifact` **不**触发
  （只改 LRU 时间，不改结构）。
- 容量按节点数计（不是按目录数），上限 300,000 个 `Node`（21.8 万项场景也装得下，
  约 13MB），超出按 LRU 淘汰。
- 同一目录未命中时用 single-flight：一个请求生成，其余等待者共享结果；等待者尊重
  自己的 `ctx`，不会因为别人算得慢而拖死。**错误不入缓存。**

### 2. PROPFIND 响应缓存（`internal/webdav`，按请求分片）

- 键 = 结构版本号 + 请求路径 + `Depth` 头 + 基地址（Season 内的 `.strm` 长度依赖它）
  + 请求体 SHA-256（不同客户端要的 prop 集不同，返回的 XML 不同）。
- 值 = 状态码 + 响应头 + 完整响应体。命中时直接回放字节，跳过 DB、结构计算与 XML 序列化。
- 只缓存 `207 Multi-Status` 且完整写完、未超单条上限的响应；请求体超过 64KB 不缓存。
- 容量：单条上限 16MB、总量上限 64MB，LRU 淘汰。两个常量写在代码里，不做成 settings
  ——它们没有运维语义，调大只会让进程更容易 OOM。
- **认证在缓存之前**：`ServeHTTP` 先做 Basic 认证，通过后才能命中缓存；缓存里不含
  任何跨凭据共享的内容。
- 并发未命中同样 single-flight，后来者等结果而不是一起重算。

### 3. 失效语义（对应 issue 里的五个点）

| 场景 | 机制 | 结果 |
| --- | --- | --- |
| 同步落库新增/删除分类、剧、集 | 写方法提交后 `TreeRevision()+1` | 下一次请求必冷算，立刻看到新数据 |
| `settings` 热改（含 `merge_chunk_size`） | `Settings.Set*` 后 +1 | 立刻按新配置重算，不读旧结构 |
| 剧/分类元数据变更 | 走同一条 `changed()` 路径 | 同上 |
| 并发同一路径未命中 | single-flight | 只算一次，等待者有 `ctx` 超时 |
| 内存上限 | 节点数 / 字节双上限 + LRU | 有界 |
| DB 停机 | 认证阶段就失败 | 仍是 401，不会变成 5xx |
| 重启 | 缓存随进程消失 | 冷启动按需重建，不阻塞启动 |

## 理由

- 版本号用一个 `atomic.Uint64` 就把「哪种写入该失效哪棵子树」的全部复杂度消掉了。
  按子树精确失效需要把每个写路径都映射到目录键，漏一条就是用户看不到新数据；
  而冷算一次最贵的目录也只有几十毫秒，代价远小于正确性风险。
- 结构缓存解决 DB 压力，响应缓存解决序列化与投递——两者针对的是 profile 里两段不同
  的开销，缺一不可。
- 不引入 Redis 之类外部缓存（硬约束 4），也不落盘（硬约束 1）：缓存只是加速视图，
  进程重启后从数据库重建即可。

## 被否方案

- **只做结构缓存**：实测最多省 30ms，达不到 50ms 门槛。
- **按子树精确失效**：写路径与目录键的映射分散在 sync、web、播放多处，任何一个新增
  写方法忘记登记就是「同步完看不到新剧」；收益只是省掉其他目录的一次冷算。
- **缓存 `Tree.Render` 的文件字节**：`.strm` 内容随基地址与签名变化，`.nfo` 很小，
  收益低而键空间大；本 ADR 不动它。

## 后果

- 每次结构性写入会让下一次 PROPFIND 冷算一次（同步结束后第一屏略慢），之后恢复。
  这是有意的正确性取舍。
- 进程常驻内存增加：结构缓存的容量闸门是 300,000 个 `Node`，但单个节点的实际开销
  远大于早期「约 13MB」的估算——功能检测一轮全库扫描后 VmHWM 到 423MB（含扫描本身
  的工作集）。该上限只保证有界、不承诺低占用；全库扫描场景的容量与收益需另行评估。
  响应缓存上限 64MB，8,329 档 body 4.5MB，常驻增量在 10MB 内。
- 21.8 万项档的响应体 114MB 超过 16MB 单条上限，**不进入响应缓存**，墙钟仍是 4s 量级
  （仍在 651 契约 ≤5s 内），响应体 >100MB 属于协议下限，缓存无法消除；10 万档 52.9MB
  同理。这两档的改善来自结构缓存（少一次全量 DB 读 + 派生），而非响应回放。
- 范围说明：本 ADR 的实现动了 `internal/vfs`、`internal/store` 与 `internal/webdav`，
  并新增 `internal/lru`。父 issue（MKACG-603）原写「669 只动 vfs 与 store」，扩展的
  依据就是上面的 profile——只在 vfs 层做达不到验收硬门槛；`internal/webdav` 不在
  MKACG-665（web 删除）与 MKACG-667（模板重写）的改动范围内。
