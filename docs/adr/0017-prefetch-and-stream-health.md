# ADR-0017：播放触发的整剧直链预取与失败退避

状态：**已接受**（2026-11-04，MKACG-681）

## 背景

ADR-0016 把直链连同 `expires_at` 落库之后，**同一块内**的重复播放已经零外呼。
冷启动还剩下两个成本（MKACG-603「冷启动三刀」的第二刀）：

- 播放列表每次请求仍要为整块成员解析一次直链。库里未过期的集不解析，但**没播过的集**
  一个都没有 —— 第一次播放第 N 块，仍要等一次页面请求（红果侧约 1/10 概率「200 + 空体」，
  换成 502 或超时）；
- 用户拖到**相邻块**时，那一块的成员全是「没播过的集」，于是再等一整块解析 + 逐集
  `ffprobe`（`ServePlaylist` 的时长补齐）。拖一下卡一下，是整剧浏览最明显的卡顿。

这两件事都可以在「已经开播」这个前提下提前做：用户正在看第 1 块时，把整部剧的直链
先申请好；拖到第 2 块就是缓存命中。

## 决策

### 1. 触发点只有播放列表成功之后

`ServePlaylist` 在 `timelineFor` 成功、响应写出**之前**调 `kickPrefetch(dramaID, u.eps)`：
此时当前块成员必然已经落库（播放列表的解析路径），预取从「下一块」开始就有真实收益。

- **分片端点不触发**：拖动会让 `ServeSegment` 反复到来，每来一次就重启任务，等于把
  后台任务变成前台请求的副作用；播放列表本来就是一次播放的起点。
- **非阻塞**：`kickPrefetch` 只加锁、起 goroutine，不查库、不等待。预取结果永远不进入
  当前请求的返回值 —— 预取失败不影响这一次播放。

### 2. 预取只复用 `Resolver.DirectMany`

预取器（`internal/segment/prefetch.go`）只调用 `Cutter.resolveMany`（装配根注入的
`stream.Resolver.DirectMany`）：

- 缓存判定（未过期直接命中）、单飞（同一集并发只解析一次）、落库、通道判据
  （`stream.ChannelOf`）都只有那一份实现；
- 预取**不是第二条解析路径**：没有预取专用的 `Resolve` 方法，没有绕过缓存的批量入口，
  也没有新的插件契约。

### 3. 计划是纯函数，优先级固定

`prefetchPlan(blocks, current, fails, now)`（无 I/O、无时钟读取）：

1. **当前块**：用户正在看的这一块（块内直接拖拽）；
2. **下一块**：拖到相邻块的第一片 —— 这是整剧浏览最常用的跳跃；
3. **其余块**：含已经播过的更早的块，按 `ep_no` 升序。

块来自 `Store.DramaBlocks`（现读 `merge_chunk_size` + `chunkEpisodes` 唯一实现），
预取不自己再切一遍（硬约束 6）。退避期内的集从批次中剔除；整块都被剔除时该批消失。
**缓存命中与否不在计划里过滤** —— 那是 `DirectMany` 的判定，计划只回答「哪些集允许被尝试」。

### 4. 失败状态独立建表，前台从不读

```sql
episode_stream_fail(episode_id PK, reason, failed_at, retry_after)
```

为什么不写进 `episode_stream`：那张表的主键是 `(episode_id, channel)`、`url NOT NULL`，
而失败时**还没有可信通道**（App 通道的换身份限流发生在解析过程中，没拿到直链就判不出
web / app）。为了记一次失败去放宽 `channel` 的 CHECK、塞空 url，会把「已入库直链」的
语义搅浑；分表还让「作废直链」不连带删掉失败记录。

`reason` 的取值由 `stream.FailureReason` 一处判定（`rejected / upstream / schema /
no_stream / login / unsupported / other`），segment 不判断插件哨兵。前台错误矩阵
（`segment.playErr`）按自己的语义映射状态码，两张表互不影响。

**失败是批级的**：`DirectMany` 是整块原子操作，一个成员失败整批报错，于是整批成员记
同一条失败记录、同一退避时刻。代价是「一集坏了整块退避 900 s」；要精确到集需要插件
返回带集号的结构化错误，那是插件契约变更，不在本刀范围。前台不受影响（它不读这张表，
播放该集时仍现解析一次）。

### 5. 退避是固定值，不做指数

- `prefetch_retry_sec`（默认 900，范围 60–86400）：失败集的下次可预取时刻 = 失败时刻 + 本值；
- 一次任务对每一集最多尝试一次（计划里每集只出现一次）；退避判定只看
  `retry_after > now`，不数失败次数、没有健康分；
- **不做指数退避**：源侧「200 + 空体」是偶发抖动（MKACG-677 实测约 1/10），指数退避会把
  第三次失败推到小时级，那时前台早就用同步解析兜住了 —— 后台预取的收益反而归零。

### 6. 并发上限：`prefetch_concurrency`（默认 1，0 = 关闭）

一批 = 一个合并块，`prefetch_concurrency` 是同时在途的批数上限。默认 1（串行）：源侧
App 通道换身份有 ≤1 次/分钟的限制，后台预取不该和前台抢配额；`0` = 整段关闭
（与 `refresh_batch` / `cache_max_mb` 的「0 = 关」同一约定）。两项配置都在任务开始时
读一次：一次任务的并发与退避口径必须一致，中途改值留给下一次播放触发的任务。

### 7. 任务 ctx 与播放请求解耦（硬要求）

预取任务的根 ctx 是**进程 ctx**（`StartPrefetch` 注入），不是触发它的播放请求 ctx：

- 请求结束（响应写完）不取消任务；
- **「不再起新批」与「中断在途批」是两个信号**：换剧只关任务的 `stop`，**尚未开始的
  批次被丢弃**；只有进程停机（`StopPrefetch`）才 cancel 任务 ctx；
- **在途批不中断**：`Resolver` 的 flight 是单飞，owner 的失败会原样传播给所有等待者。
  如果换剧就把 owner 的 ctx 取消，同一集的前台等待者会读到 `context.Canceled`，被映射
  成 502 —— 后台任务把前台打挂，这是不能接受的。一批最多一个合并块（默认 10 集），
  多跑一次的量有界；
- **并发上限是进程级的**：换剧后新任务先等旧任务在途批收尾（`prev.done`）再开始，
  不会出现两个任务的信号量各算一份、切剧瞬间翻倍外呼。

停机取消导致的失败**不记退避**（换剧根本不取消在途批）：记下来会让这些集在退避期内
不被任何任务碰（而它们其实没被真正尝试过）。

### 8. 只给「下一块」补时长

下一块解析成功后，对其中 `duration_sec == 0` 的集做一次 `ensureDuration`（ffprobe +
回填），前提是 ffmpeg 闸空闲（有前台转封装在跑就让路）。这样拖到下一块时，播放列表的
`EXTINF` 也不需要现探测。当前块播放列表已经探过；其余块收益低且工作量无界，不做。
失败只记 debug —— 下一次播放列表仍走原来的现探测路径。

### 9. 修掉 0016 的 `last_ok_at` 覆盖缺陷

`UpsertEpisodeStream` 原来无条件写 `last_ok_at = excluded.last_ok_at`，而解析落库
（`Resolver.persist`）根本不知道新链能不能用、传的是空串 —— 于是**每次刷新直链都会擦掉
「上次确认能用」**。预取会让刷新更频繁，这个缺陷影响更大。

改为：只有调用方显式给非空值时才覆盖；空串保留旧值。语义收敛为「`last_ok_at` 只由
`touchStream`（真探测/真转封装成功）与显式非空写入推进」。

### 10. 不做的事

- **不做周期巡检 / 常驻循环**：没有 `NewTicker`、没有整剧健康检查。任务只在播放列表
  成功后被踢一次，跑完即止；没人看时零上游请求（需求原文「什么时候预取？在播的时候」）。
- **不做分片预热**：本刀只申请直链，不生成 `.m4s`（那是 MKACG-682）。
- **不改 `episode_stream` 列结构、不改对外路由/`.strm`/id/HMAC 格式、不改插件契约**。

## 后果

- 播放第 1 块之后再拖到相邻块，直链零外呼；`ffprobe` 也被提前做过，首片只剩本地
  转封装/缓存的时间（测量方法与 P50/P95 见 MKACG-681 的验收记录）。
- 整剧预取会在开播后产生一串上游请求（受 `prefetch_concurrency` 与退避约束）；
  它们是可取消的，切剧后未开始的批次不再发出。
- `episode_stream_fail` 是新的排障面：按剧可查「哪些集预取失败、为什么、何时再试」。
  表中的 `reason` 不含 URL/key，不构成敏感面。
- `newHandler` 现在返回 `(http.Handler, *segment.Cutter)`：预取器的启停属于播放面
  生命周期，只有装配根知道进程何时开始/结束（不新增构造参数）。

## 回退

- 运行期：把 `prefetch_concurrency` 设为 `0`，预取立即停止（下一次播放不再起任务）；
  已在跑的任务最多把手上这批做完。
- 代码级：删掉 `ServePlaylist` 里的 `kickPrefetch` 调用即可回到「只按请求解析」的行为；
  `episode_stream_fail` 与预取器可以整体删除（不参与任何前台判定），无需数据迁移。
